# ADRC robustness fixes — call for flight testers

**English** | [Русский](ADRC_FIXES.ru.md)

This fork adds a series of **small, independent** robustness fixes on top of
[`Boyyt357/ADRC-betaflight`](https://github.com/Boyyt357/ADRC-betaflight). They came out of a
line-by-line review of the ADRC implementation in `src/main/flight/pid.c` against ADRC/LADRC
theory. The math core (LESO + virtual PD + disturbance compensation, Gao 2003 bandwidth
parameterization) is faithful; these fixes target the **robustness seam** where ADRC meets the
legacy Betaflight plumbing.

> ⚠️ **All of these are UNTESTED on real hardware.** I do not have a craft to fly them on.
> Each fix is a **separate commit**, so you can build with or without any of them
> (`git revert <sha>` to drop one). **Please flight-test and report in the issues.**

## What to report
- Craft (size, weight, motors/props, FC target), and your ADRC P/I/D (wc/wo/b0) values.
- Which commits you built with (or "all").
- Behavior: arm/spool-up, hover, hard maneuvers, prop wash, wind, recovery after throttle
  chops / desync, any oscillation or motor heating.
- Blackbox log if possible.

## The commits

| Fix | Commit subject | What it changes | Risk |
| :-- | :-- | :-- | :-- |
| `#3` defaults | `re-derive default P/I/D as ADRC bandwidths` | Default P/I/D were unconverted stock PID ints (wo/wc≈1.78); now wc=10, wo=110, b0=100 (yaw wo=80) per the proven 5" tune, with an explicit yaw b0. | Low (defaults only) |
| `#1` anti-windup | `add anti-windup clamp on the ESO disturbance estimate z3` | Bounds z3 so the disturbance term `z3/b0` stays within the per-axis pidsum limit; prevents lag in recovery after motor saturation. | Medium |
| `#2` observer feedback | `feed the ESO the saturation-limited command` | The ESO `b0*u` term now uses the pidsum clamped to the per-axis limit (what the plant can actually apply) instead of the raw pre-saturation pidsum. | Medium |
| `#4` zero-throttle | `keep the ESO running at zero throttle` | At zero throttle (no airmode) the observer was reset every loop; now it keeps integrating and only the legacy I accumulator is cleared, so the disturbance estimate survives spool-up. Genuine disarm/overflow still fully resets. | Medium |
| `#5` core-only feedback | `EXPERIMENTAL — feed ESO only the ADRC core (exclude F/S)` | Feeds the observer only P+I+D, excluding feedforward F and S-term (which aren't /b0). **Reverted on master 2026-07-02** after the hardware A/B below showed `#2` flies the same or slightly better — the default build is now the `#2` behavior. To try `#5` anyway: `git cherry-pick 0d43645`. | High / uncertain |
| `#6` gain ceiling | `raise the PID gain ceiling to the uint8_t max (255)` | The System-Gain (D → b0) input was capped at 250 by the legacy `PID_GAIN_MAX`; on fast motors the tune can need more. Raised to 255 (the hard uint8_t ceiling). Only widens the allowed range — no behavior change at existing values. Going above 255 would need a wider field (breaks MSP/blackbox). | Low (range only) |
| `#7a` anti-gravity | `EXPERIMENTAL — disable anti-gravity P-boost under ADRC` | Anti-gravity (on by default) multiplies the roll/pitch P-term during throttle transients — a legacy PID heuristic. ADRC already rejects throttle-sag torque via the observer (z3), so the boost just adds a transient overshoot at spool-up/takeoff (a likely extra cause of the takeoff bounce). Boost still logged for study; revert to A/B. | High / uncertain |
| `#7b` observer log | `add DEBUG_ADRC blackbox logging of the ESO states` | New `debug_mode = ADRC`: logs the observer states so testers can actually see them — roll z1/z2/z3 (debug 0–2), pitch z1/z2/z3 (3–5), yaw z3 (6), throttle-scaled b0 multiplier ×100 (7, sign-tagged by the fix `#8` liftoff latch: positive = airborne, negative = gated). z3 is logged ÷16 (fix `#12`) so the int16 field does not clip — multiply back to read it, or use the I channel (−z3/b0) for the disturbance magnitude. Diagnostic only, no flight-behavior change. | None (logging) |
| `#9` b0 multiplier | `add adrc_b0_scale — per-craft System-Gain multiplier` | New CLI setting: `set adrc_b0_scale = N` (1–100, default 10) makes **b0 = D × N**. Set once per craft; day-to-day tuning stays in the ordinary D cell of the Configurator. Solves the whoop case where D maxes out at 250 (with the default ×10 the ceiling is b0 = 2550; a whoop can set scale 20–40 and keep D mid-range). ⚠️ When reporting tunes, state the scale too — the same D means different b0 on different crafts. | Low (default unchanged) |
| `#8` liftoff gate | `EXPERIMENTAL — gate the ESO b0·u feed until liftoff` | Blackbox analysis of real takeoffs (see below) showed the residual bounce = z3 winding toward −b0·u while the craft is still ground-constrained (on the ground the plant does not respond to the command, i.e. effective b0 ≈ 0). Until liftoff is detected — throttle ≥ 40%, or any-axis rotation > 20 deg/s sustained 25 ms (a toss launch opens it almost instantly) — the observer's b0·u term is zeroed, so z3 stays ≈ 0 on the ground *by construction*. A brief in-flight throttle chop keeps the full observer; the gate re-arms only after a sustained return to idle (fix `#10`). | High / uncertain |
| `#10` throttle-b0 | `EXPERIMENTAL — throttle-scaled b0 + gate re-arm` | Two parts. **Throttle-scaled b0:** motor authority scales with RPM and thrust ≈ throttle², so a b0 tuned at hover is wrong away from it; b0 is now scaled by `(throttle/hover)²`, clamped to [1, 9] — only *up* from hover (scaling down would make 1/b0 huge and inject extreme output at low throttle). New CLI `set adrc_hover_throttle = N` (%, default 35). Aimed at the whoop takeoff-drift and "floaty" feel where a high thrust/weight ratio makes the hover-b0 error large. **Gate re-arm:** the fix `#8` liftoff latch now re-arms after throttle stays below 5% for 200 ms, so every ground-test rep in one arm is gated — fixes the "re-takeoff not re-gated" limitation of `#8`. | High / uncertain |
| `#11` z3 decay | `EXPERIMENTAL — leaky decay on the ESO disturbance z3` | z3 becomes a leaky integrator: `z3 += dt·(−β3·e − decay·z3)`, so a transient bump bleeds off instead of lingering. New CLI: `adrc_sigma_decay` (rate ×0.1, default 3 → a mild leak, τ ≈ 3 s; set `0` for the classic pure integrator) and `adrc_sigma_decay_sched` (schedule gain ×0.01, **default 0 = off, leave it there**). The scheduling was meant to hold a sustained disturbance, but the low-pass it keys on tracks observer *transients* (maneuvers, prop-wash), not steady load — the observer drives its error to ~0 while z3 correctly holds a constant disturbance — so `_sched` is unvalidated. | High / uncertain |
| `#12` z3 log scale | `scale down z3 in DEBUG_ADRC to stop int16 clipping` | Raw z3, logged in the same units as z1/z2, overflowed the int16 blackbox field under strong disturbance (the "debug 5/6 go nuts on takeoff" report) — it saturated ±32767. Now logged ÷16 **and saturated to ±32767** — `debug[]` is int16 and `DEBUG_SET` does not range-check, so an over-range value *wraps* into garbage; on high-b0 builds the z3 anti-windup clamp (b0 × pidsum limit) can exceed int16 even ÷16, and a flat rail on a plot honestly reads "off-scale" while a wrap reads as noise (v0.2.0 hex: readable to ±524k, wraps past that — use the I channel there). z1/z2 saturated the same way. debug[7] also switched from ±b0 to the ±throttle-scaled multiplier ×100. Logging only. | None (logging) |

## Known real-world feedback (as of July 2026)

Real-flight evidence for the ADRC-Betaflight fork is currently very thin (the fork is only days old). Collected here so the picture stays honest:

**Flights of this fork**
- **Author demo** — Boyyt357, YouTube *Engineering Robotic*, [BLTQN-Gw7LE](https://www.youtube.com/watch?v=BLTQN-Gw7LE): a 10" quad flown with uncalibrated params (P10/I50/D20) and a water-bottle payload swinging off one arm. Proof-of-concept; per comments the clip reportedly ends in a crash.
- **One independent pilot — jmsweng** ([PR `#1`](https://github.com/Boyyt357/ADRC-betaflight/pull/1)): flew a 5" quad carrying an unstable load (~40% of AUW), toss-launched with PID off at min throttle, params 10/110/100. The only third-party flight found.
- **Negative hands-on report** — YouTube commenter @captain-ulitka: on a normal build the controller "barely resists external influences" and oscillates when the gains are raised. Worth watching for during testing.
- **Update (2026-06-30, [issue `#1`](https://github.com/danusha2345/ADRC-betaflight/issues/1)) — jmsweng** ran more flights on a 5" (640 g, DAKEFPVF405, 4S, 2300 kV) and reported a **strong positive disturbance-rejection result**: a leaf-blower and a stick strike mid-air did not meaningfully destabilize it, and it flew with 20–40% of AUW offset on one motor arm. He also derived the step-by-step **tuning procedure** now in the README (ending at 40/160/200). Open question he surfaced: the rate **ESO doesn't model gravity**, so throttle-up shows a brief sub-second bounce/oscillation before it settles — a likely cause of the "unpredictable on arm" reports, and a candidate that fixes **`#4` (keep ESO at zero throttle)** and **`#1` (anti-windup)** may affect. (Caveat: his tests were on the original code with a damaged motor; re-test pending.)
- **✅ Hardware validation (2026-07-01, [issue `#1`](https://github.com/danusha2345/ADRC-betaflight/issues/1)) — jmsweng** A/B-tested this fork against the original firmware on his 5" (640 g, DAKEFPVF405, 4S, now 1750 kV, params 40/160/250) with **blackbox logs**:
  - **The takeoff bounce is fixed.** The original firmware still bounces/shakes at takeoff even after a motor swap; builds with **fix `#2` or fix `#5` take off cleanly**. Blackbox confirms fewer start-up oscillations with either fix, and **fix `#2` damps out faster** → fix `#2` is the recommended baseline; fix `#5` (EXPERIMENTAL) flew nearly identically and *maybe* slightly worse under a hanging load, so it stays optional.
  - **Disturbance rejection confirmed hands-on:** he could set the quad down and balance it on a single motor and it stayed stable (⚠️ he cut himself doing this — do not attempt near a spinning 5").
  - **Chattering at the gain ceiling:** at D=250 (b0=2500) he still heard occasional chatter, and lowering the gain made it worse. He hit the old 250 cap wanting ~263 for the faster motors. Fix **`#6`** raises the ceiling to 255; beyond that the real lever is re-tuning observer bandwidth (I/wo) / gyro filtering for the new motor vibration, not more gain.
  - Zero-throttle "sticks at the last attitude it touched down at" — expected side effect of keeping the ESO alive (fix `#4`); jmsweng considers it a harmless ADRC quirk.
- **✈️ Airfield tests (2026-07-01, [issue `#1`](https://github.com/danusha2345/ADRC-betaflight/issues/1)) — jmsweng**, now on the full fix stack including **`#7a`** (anti-gravity off), re-tuned to **30/100/200** on the 1750 kV setup. Verdict: *"In its current state, this method seems to be superior to PID control."*
  - **Wind rejection felt in flight:** the quad noticeably did not drift when the wind picked up (consistent with the earlier leaf-blower test).
  - **~20% AUW hung off motor 4:** flyable but "handles like crap"; blackbox shows motor 4 pinned at max output for a large share of the flight — a **thrust-ceiling limit, not a control limit**.
  - **Prop-damage tolerance:** a crash severely bent two props → flew back normally, only the noise gave it away. He then **cut one blade off** prop 2 (plus two bent blades on prop 3) and it *still* flew acceptably, until vibration loosened the arm screws and ejected the arm.
  - Residual takeoff oscillations are still visible in blackbox even with `#7a`, but no longer visible/audible in person. He keeps `#7a`: anti-gravity duplicates what the observer already does.
  - He also proposed picking tunes **quantitatively** from the variance of the takeoff/hover blackbox traces — plots of the same maneuver under different tunes separate clearly.
- **🔬 Maintainer blackbox analysis (2026-07-02)** of the logs above (charts in [`docs/flight-test-analysis/`](docs/flight-test-analysis/)):
  - **The takeoff bounce tracks z3 windup on the ground.** In the four-tune takeoff A/B, tunes where pitch z3 (the I-term) wound up to ~+65…+90 during spool-up bounced (pitch tracking-error RMS 13–19 deg/s in the first airborne second); tunes where z3 stayed ≈0 took off clean (RMS 3–5 deg/s). Single-run data, but it localizes the mechanism: while the craft is ground-constrained the ESO mis-attributes thrust to a phantom disturbance, which then has to unwind at liftoff. → strongest candidate for the next fix: ground-transient handling of z3 (gate or slew-limit it until liftoff is detected).
  - **Load flight:** motor 4 at ≥99% output ~12% of the flight — confirms the power-limit reading.
  - **Prop-damage flight:** unfiltered-gyro vibration PSD ~20× the intact-prop flight across the band, whole-flight tracking-error RMS ~3.7× higher — and still controllable. A strong disturbance-rejection data point.

- **🐣 First whoop test (2026-07-03, [issue `#1`](https://github.com/danusha2345/ADRC-betaflight/issues/1)) — jmsweng**, Air65 (65 mm, 25 g, 1S, 30000 kV) on `BETAFPVG473_V2` with fix `#8` aboard. Flew and tuned (best ≈ 15/65/250), but **maxed out D=250 wanting more b0** — the trigger for fix **`#9`** (`adrc_b0_scale`). Maintainer log analysis: the fix `#8` liftoff gate works on hardware (pre-liftoff |I| peaks 8–51 vs 60–90 on the ungated 5"; the disturbance estimate now grows only after liftoff), and the one unstable tune with ωo=80 shows the observer oscillating on frame vibration (|I| to ±330) — the whoop's observer-bandwidth ceiling is real. Remaining takeoff drift with an offset battery = z3 honestly learning the CG torque after liftoff (~1/ωo), aggravated by the compressed tune the b0 ceiling forced.
- **📣 First public exposure (2026-07-03):** jmsweng posted a call for testers on [r/fpv](https://www.reddit.com/r/fpv/comments/1um3q8m/adrc_instead_of_pid_control/) (honest framing: "no tuning" is not true, but disturbance rejection is remarkable — prop-cut flight, single-motor balancing). Prebuilt hex for 16 popular boards now ship via [GitHub Releases](https://github.com/danusha2345/ADRC-betaflight/releases) to lower the entry barrier he flagged.
- **🤝 Second independent tester + fix `#8` A/B (2026-07-04/05):** a second developer ([SeverinBitterli](https://github.com/SeverinBitterli/betaflight/tree/ADRC-Implementation)) running an *independent* ADRC implementation on a BetaFPV Pavo20 Pro (2" cinewhoop) confirmed stable hover and a working angle mode — the same degree-2 3-state LADRC core reached independently, already borrowing this fork's `adrc_b0_scale` and liftoff gate. jmsweng re-tuned the Air65 with `adrc_b0_scale = 20` to a working **33/65/160** (the "floaty" feel went away by raising ωc relative to ωo, away from the 3–5× rule of thumb) and posted the first logs with `debug_mode = ADRC` actually enabled — an A/B of fix `#8` plus fan-disturbance takeoffs. Maintainer analysis of those logs: the gate latches correctly (debug[7] shows gated→air), but on a 30000 kV whoop flown indoors the ground-windup A/B is swamped by vibration and furniture strikes — a clean vertical takeoff (ideally on the 5") is still needed to isolate it. The raw z3 debug field also saturates int16 under strong disturbance (the "debug 5/6 go nuts" report → fix `#12`), and the observer's disturbance estimate routinely hits the pidsum limit. Fixes **`#10` (throttle-scaled b0 + gate re-arm)**, **`#11` (z3 leaky decay)** and **`#12` (z3 log scaling)** came out of this round, incorporating two of Severin's ideas (throttle-scaled b0, scheduled z3 decay).
- **🛬 Round-2 5" flight logs — gate confirmed, control-bandwidth noise ceiling (2026-07-05/06):** jmsweng flew the shipped `adrc-v0.2.0` on a 5" and swept the control bandwidth. Analysis: **(1)** the liftoff gate works on real hardware — on our v0.2.0 layout `debug[7]` is negative (gated) on the ground and flips positive once airborne; the fix `#10b` re-arm is confirmed too (two mid-arm landings re-gated at idle+stillness, then re-opened for the next hop). **(2)** The "loud horn/chatter on throttle-up" at higher control bandwidth ωc is the control law amplifying residual gyro noise — motor HF noise roughly doubled from ωc 30→60 and jumped a further 50–78% on throttle-up, while the gyro's own HF content stayed low. ωc has a **practical ceiling set by gyro noise**, not stability; the 5" sweet spot was **60/100/200**. **(3)** throttle-scaled b0 (`#10`) is flight-validated: "far better than stock PID", flew with bent props on three motors, no softness-at-full-throttle complaint (the quadratic-exponent caveat did not bite). **(4)** The v0.2.0 hex still wraps z2 and rails z3 under hard maneuvers (b0·PIDSUM on a 5" is 1e6, ÷16 still exceeds int16), which retro-justifies the debug-saturate commit. **(5)** In ~25 km/h wind `axisI` pegs at `PIDSUM_LIMIT` and motors saturate 26% of the flight — a physical thrust ceiling. The dedicated fix `#8` A/B turned out to be **invalid, not just noisy**: the log headers show all four flights — including the two labeled "with fix 8" — on the same `jmsweng/testing @ 2a1a056c6` build, which is this fork *with fix `#8` reverted*; the "with" arm was never flown. A real A/B (release hex vs gate-reverted build, header-checked) is deferred to round 3. Open architectural idea (candidate fix `#13`): low-pass `z2` in the control law only, to lift the ωc ceiling at the cost of D-action phase lag — needs its own A/B.
- **🛠️ Third craft — maintainer bench+hover validation, and a gyro-freeze trap (2026-07-07):** the maintainer flew the current master (`e4f9feaa0`) on his own 5" (2207 1300 kV, 6S, 51477 props, Diatone Mamba MAMBAF722_I2C). **Honest scope: a short indoor hover over the floor** — but it flies and handles: tracking error mean 1.8 °/s (p95 = 5 °/s) on roll, no oscillation (a ~100 Hz bench limit cycle at idle prompted raising `adrc_b0_scale` 10→20, i.e. b0 = 4000 — but the cycle later traced to a stick / `pid_at_min_throttle` artefact, **not** b0, so scale = 20 on a 5" is *unvalidated* and wants a clean 10-vs-20 A/B; a 5" usually reaches its b0 at the default scale = 10, the ×20 headroom is really for authority-limited whoops that hit the D ceiling), and the liftoff gate + re-arm (`#8`/`#10`) worked textbook: 12.5 s of armed ground idle fully gated, clean opening at takeoff throttle, re-arms on mid-arm landings. Two lessons for other testers landed in the docs: **(1)** on this board + the 2026-alpha base, `dshot_bidir = ON` caused **hard gyro freezes** (thousands of identical gyro samples mid-flight — the craft is momentarily uncontrollable); if your craft acts possessed, try `set dshot_bidir = OFF` (you lose the RPM filter; dyn_notch still works). **(2)** `pid_at_min_throttle = off` makes the controller fully asleep at idle — on a bench it reads as "the sticks do nothing"; with the gate in place the stock ON is safe (README updated with the trade-off).

- **⚠️ Round-3 freestyle findings — two defects in the *validated* fixes themselves (2026-07-10, via upstream PR [betaflight#15400](https://github.com/betaflight/betaflight/pull/15400)):** the first freestyle blackbox on the PR port of this fork's fixes (SpeedyBee F7 Mini 5", ACRO, 71 s) exposed two problems that live in this fork's own code too — hover/racing flights simply never hit them. **(1) Fix `#10b`'s gate re-arm false-triggers mid-air:** a smooth zero-throttle float (gyro 1–4 °/s for > 500 ms — routine in freestyle) is indistinguishable from a landing by throttle+gyro, and the log shows three in-flight gate closures, each dumping the live z3 and blinding the ESO to b0·u — which airmode keeps applying, hence "don't use airmode" reports and wobble on throttle catches. Upstream fix: re-arm is now **opt-in, default off** (`adrc_liftoff_idle_hold_ms = 0` — gate stays open from first liftoff until disarm). *This fork's master keeps the always-on re-arm: avoid zero-throttle floats/airmode freestyle on fork builds, or fly the PR builds.* **(2) Fix `#10a`'s quadratic b0 scaling under-gains punches when `adrc_hover_throttle` is set low:** at hover = 22 % a 59 %-throttle punch ran scale ×7.4 (ceiling ×9 from 66 %) — uncommanded 180 °/s pitch excursion with motors at 1411/2047 (no saturation, pure lack of gain), z3 wound to 524k. The quadratic law was only ever validated to ~×3; upstream capped the default `adrc_b0_scale_max` at 3 (fork hardcodes 9 — same caveat applies).

**No wider traction yet (forums):** no Reddit / RCGroups / IntoFPV / blog threads on this fork, and the official Betaflight project has zero ADRC mentions (issues/PRs/discussions).

**Broader ADRC on multirotors (not this fork, research)** — genuine real flights that favor ADRC for disturbance rejection, but always with *tuned* ADRC on research rigs:
- Lv et al., *Sensors* 2024 — LADRC quad autonomously landing on a moving USV; landing accuracy ~0.057 m vs ~0.11 m for PID. [PMC10935343](https://pmc.ncbi.nlm.nih.gov/articles/PMC10935343/)
- Michalski et al., ICUAS 2023 — ADRC vs PID position control on a Crazyflie 2.1 (OptiTrack mocap), real indoor flights. [IEEE 10156505](https://ieeexplore.ieee.org/document/10156505/)

**Reality check on "no tuning":** ADRC for quads has many parameters, and a whole research subfield exists just to auto-tune them (GA/PSO/Kriging); PID still covers ~90–97% of UAV applications. ADRC is a capable disturbance-rejection approach, but "PID killer / no tuning" is marketing, not an established field result. This is exactly why these fixes ship **with a call for testers** rather than as proven defaults.

## Background
The full theory-vs-implementation review (what matches canonical LADRC, what is a deliberate
simplification, what deviates, and the robustness concerns these commits address) lives outside
the firmware tree in the maintainer's notes; the short version of each concern is in the commit
messages. Questions and results → **open an issue**.
